# تشغيل الطابور ومراجعة مخرجاته

## الحفظ والتزامن

يكتب الخادم الرسالة والمهمة في معاملة SQLite واحدة. يستخدم المتصفح معرّفًا ثابتًا عند إعادة محاولة الطلب. يُسمح بستين مهمة جديدة لكل مشروع خلال ساعة. تُعرض أحدث 500 رسالة و100 مهمة لكل مشروع وتبقى البيانات الأقدم في القاعدة. عند الترقية أوقف العامل القديم والواجهة القديمة وخذ نسخة خاصة من مجلد البيانات أولًا. يستورد الإصدار الجديد ملفات المحادثة والطابور القديمة مرة واحدة، ويحفظ الأصول. راجع الطلبات القديمة يدويًا قبل إعادة تقديمها.

يأخذ كل عامل حجزًا للمشروع وللمزود معًا. ينتظر العامل طلبًا آخر إذا كان Codex مشغولًا ولو كانت المهمتان لمشروعين مختلفين. المهمة التي تحتاج معيار اختبار يمكن إكمالها من نفس الواجهة قبل إرسالها للمحرك. تؤجل الطلبات ذات إشارات النشر أو الدفع إلى موافقة مستقلة. تظل قيود العزل مطلوبة لأن النص قد يصوغ هذه الأفعال بطرق مختلفة. نتيجة CLI الناجحة تنتظر مراجعة الفروقات والاختبارات.

## استئناف العمل

- تستمر المهام المعلقة تلقائيًا عند إعادة تشغيل العامل. إذا فشل الاتصال أو الدخول **قبل أي تنفيذ** يظهر خيار استئناف المهمة نفسها بعد إصلاح الصلاحية. يمكن لمسؤول الخدمة أيضًا تشغيل الأمر التالي داخل بيئة العامل التي تحتوي على مسار البيانات الصحيح.

      node worker.cjs --resume TASK_UUID

- إذا انقطع العامل بعد استلام المهمة، تظهر الحالة `interrupted` بعد انقضاء حجز 90 ثانية ودورة فحص العامل التالية. افحص المحرك وحاويتي المهمة ونسخة Git الخاصة بها. بعد التأكد من توقف جميع العمليات وحفظ آثارها، يحرر المسؤول الحجزين بالأمر التالي. تبقى النتيجة في `needs-verification`.

      node worker.cjs --reconcile TASK_UUID --confirmed-stopped

- لا يفيد الاستئناف اليدوي في خطأ حصة أو نتيجة غامضة بعد بدء التنفيذ. راجع نقطة الحفظ والمخرجات أولًا. قد يحتوي ملخص الوكيل على ادعاء يحتاج اختبارًا مستقلًا. راجع حالة الإشعارات وإذن الجهاز من الواجهة.

## تسليم التعديلات الخاصة إلى المالك

1. تحقّق من رقم المهمة والمشروع وحالة `needs-verification` وسجل الاختبارات. نفّذ `bash ops/export-task PROJECT_ID TASK_UUID` من نسخة الكود المعتمدة على الخادم. يستخرج الأمر فرق الملفات الملتزم بها مقابل نسخة المصدر المنقحة المثبتة للمهمة، داخل حاوية قراءة فقط مفصولة عن الشبكة. يفحص الفرع والملفات غير الملتزم بها وتسلسل Git. تأتي هوية اللقطة النظيفة وSHA الأساس الأصلي من سجل خاص يكتبه المحرك عند إنشاء المهمة. لا تتغير هذه الهوية إذا حدّث المشغّل نسخ المشاريع لاحقًا. لا تستخدم ملف `changes.tmp` من محاولة فاشلة.
2. يجمع مجلد المراجعة الخاص `changes.patch` و`base` و`SHA256SUMS`. انقل المجلد إلى جهاز المالك بقناة SSH الخاصة وتحقق من البصمات. احتفظ بمحتوى المحادثات والبيانات الفعلية خارج المستودع. يقتصر التصدير على فرق الملفات دون تاريخ الالتزامات أو رسائلها.
3. افحص الفرق كاملًا محليًا، بما فيه الملفات الجديدة والأسماء وملفات الإعداد والمسارات الحساسة. افحص الأسرار وآثار بيانات العملاء وملفات النشر والتوقيع وCI. إذا أضافت المهمة ملفًا كان موجودًا في SHA الأصلي واستبعدته عملية التنقية، توقف واحتفظ بالملف الأصلي. توقف عند محتوى ثنائي غير مراجع أو شك في مصدر ملف. استخدم أداة الفحص المعتمدة لدى المشروع. النص الذي يعرضه الوكيل وحده لا يثبت سلامة الفرق.
4. على جهاز المالك، استخدم نسخة Git موثوقة منفصلة، وتحقق من `origin` وSHA الأساس الفعلي والفرع المعتمد. نفّذ المثال التالي بعد استبدال المتغيرات بالقيم المراجعة. يجب أن يكون اسم فرع المراجعة جديدًا، وأن يجري التحقق من قواعد Actions والربط الخارجي لتأكيد أن الرفع إلى هذا الفرع لا يطلق نشرًا تلقائيًا. عند تعذر هذا التحقق، احتفظ بالفرق في مسار المراجعة الخاص.

       git switch -c "review/agent-$TASK_UUID" "$BASE_SHA"
       git apply --check "$PRIVATE_PATCH"
       git apply --index "$PRIVATE_PATCH"
       git diff --cached --check
       git diff --cached --stat
       git diff --cached

5. شغّل اختبارات القبول في بيئة معزولة، وراجع النتيجة قبل إنشاء التزام جديد برسالة يكتبها المالك. سجّل المشروع وSHA واختباراته في سجل المهمة الخاص. بعد موافقة المالك على المحتوى المحدد، ارفع من **جهاز المالك** إلى اسم الفرع المراجع فقط. تحقّق من عدم وجود الفرع البعيد قبل الرفع مباشرة، واستخدم اسمًا جديدًا إذا سبق حجز الاسم.

       git ls-remote --heads origin "refs/heads/review/agent-$TASK_UUID"
       git push origin "HEAD:refs/heads/review/agent-$TASK_UUID"

   يجب أن تكون نتيجة فحص الفرع البعيد فارغة. طابق الـ SHA المحلي بالمرجع البعيد عبر `git ls-remote`. يتطلب دمج التعديل أو النشر أو إرسال التطبيقات للمتاجر موافقة منفصلة. يحتفظ العامل بنسخة المهمة على الخادم ولا يحصل على بيانات اعتماد الرفع.

## النسخة الخاصة للطابور

بعد إيقاف خدمات الوكيل أو الانتظار حتى تنتهي المهام الجارية، يستخدم المسؤول `node backup.cjs save SOURCE NEW_PRIVATE_DIR`. إذا كانت قاعدة المصادقة على وحدة منفصلة عيّن `AGENT_AUTH_DIR` إلى مسارها قبل الحفظ. يرفض الأمر مسارات Git والمجلدات الموجودة والمهام الجارية، ويختبر سلامة كل قاعدة. شغّل `node backup.cjs restore BACKUP NEW_DATA_DIR` لاختبار الاستعادة إلى مجلد جديد. يعيد النسخ إلى `queue.sqlite` و`web/auth.sqlite` ويطلب تسجيل الدخول والإشعارات مجددًا. حافظ على صلاحيات الوصول المقيدة. هذه نسخة محلية غير مشفرة، يلزم مخزن مشفر خاص لنقلها خارج الخادم. راجع تعليمات تشغيل الخادم لنسخ هويات الخدمات ومحفوظات Git ومجلدات عمل المهام بصورة منفصلة.
