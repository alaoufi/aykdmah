# بوابة فهم الطلب والإتقان — إلزامية لكل وكيل

## الهدف
منع سوء الفهم، تكرار إنشاء الميزات، والتسليم الصوري الذي يحتاج المستخدم إلى تعقب طويل بعده. هذه وثيقة شروط قبول؛ **لا تعني أن المحرك يفرضها برمجيًا بعد**.

## 1. مرحلة الفهم قبل أي تعديل
- اقرأ طلب المستخدم وسياق المشروع وقراراته وآخر تسليم، وافحص الشفرة بحثًا عن التطبيق القائم. لا تبدأ من الصفر.
- اكتب تعريفًا قصيرًا للنتيجة المطلوبة بلغة المستخدم: السلوك، المكان، المنصات، الحالات الاستثنائية، وما ليس ضمن النطاق.
- صِغ معايير قبول قابلة للاختبار من واقع الطلب؛ لا تستبدل الهدف بحل أسهل من عندك.
- ميّز الحقائق عن الافتراضات. عندما تكون هناك فجوة **مؤثرة** على السلوك أو بيانات المستخدم أو الرسوم أو التوافق أو صلاحيات النشر، اسأل أسئلة محددة وعميقة في مجموعة صغيرة مترابطة، مع بيان أثر كل إجابة.
- لا تسأل عن تفاصيل يمكن إثباتها من الكود أو الوثائق. ولا تعيد سؤالًا سبق أن أجاب عنه المالك.
- **لا تبدأ بتنفيذ خيار تخميني** إذا كان الخلاف سيؤثر في المنتج. ضع المهمة بحالة `needs-clarification` وانتظر جواب المالك، مع إمكانية إنجاز الفحوص غير المؤثرة.

## 2. خطة التنفيذ ومنع التكرار
- ابحث عن الملفات والوظائف والاختبارات الحالية، وقارن الحل المقترح بها.
- ضع خطة بأصغر تغيير ممكن وقائمة ملفات متوقعة وخطة اختبار وتراجع.
- افحص سجل Git والمهام الجارية لتفادي تحرير الملفات نفسها مع وكيل آخر.
- حدّث الوظيفة القائمة بدل إنشاء نسخة موازية. يمنع تكرار الصفحة أو API أو المكونات دون مبرر موثق.
- قسّم العمل إلى أجزاء قابلة للتحقق؛ بعد كل جزء commit واضح وحفظ في فرع المهمة.

## 3. الإتقان والتحقق
- حوّل كل معيار قبول إلى اختبار آلي أو فحص يدوي موثق، يشمل الفشل والهواتف وحالات RTL عند الاقتضاء.
- افحص البناء والاختبارات والتكامل والصلاحيات والأداء وإمكانية الوصول بحسب المهمة.
- نفّذ مراجعة ثانية للمهام الحساسة والمتغيرات الواسعة، وراجع التغيير الفعلي لا مجرد وصفه.
- أصلح العيوب المكتشفة قبل التسليم ثم أعد الاختبارات اللازمة. لا تقل «مكتمل» مع اختبار فاشل أو لم يُجرَ.
- عند تعذر تشغيل الاختبارات أو وجود مانع خارجي، قدّم النتيجة بوصفها `blocked` أو `needs-verification` مع السبب والخطوة المطلوبة؛ لا تدّعِ إتقانًا غير مثبت.

## 4. التسليم دون تعقب
- اكتب بلغة عربية مختصرة: ماذا تغير، أين، لقطات أو أدلة عند الحاجة، الأوامر والاختبارات والنتائج، الفرع وSHA، حالة الدمج والنشر، وأي تبعات.
- إذا كان المطلوب وظيفة جاهزة، لا تعدّ مجرد كتابة ملفات أو إنشاء PR إنجازًا نهائيًا.
- لا تطلب من المالك القيام بخطوات يمكن للوكيل إنجازها بأمان بصلاحياته؛ استأذنه فقط في القرارات أو التفويضات اللازمة.
- عند التصحيح لاحقًا، استعمل نفس رقم المهمة وتاريخها، لا تبدأ مهمة مكررة.

## 5. بوابات الحالة
`new → understanding → (needs-clarification | approved-scope) → implementation → verification → review → ready-for-approval → completed`

حالات الاستثناء: `blocked`, `failed`, `paused-limit`. لا انتقال إلى `completed` قبل إتمام متطلبات معايير القبول وأدلة النجاح.

## 6. مثال
طلب: «اجعل المكالمة ترن حتى لو التطبيق مغلق».
قبل البرمجة: افحص التطبيق الحالي وAndroid وiOS والإشعارات وخدمات الخلفية، ووضّح هل المقصود إغلاق الواجهة أم إيقاف العملية قسرًا، وهل مطلوب سلوك المكالمات العادية.
بعد ذلك: سيناريوهات اختبار على جهازين، انقطاع الشبكة، رفض الإذن، وضع توفير البطارية، وظهور التنبيه. لا تعتبر نجاح اختبار متصفح دليل نجاح نظام المكالمات الأصلي.
